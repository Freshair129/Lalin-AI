# RCA: Updater artifact generation stalled at signing

## Symptom

`scripts\build_installer.ps1 -WithUpdaterArtifacts` produced a fresh NSIS setup executable but did not produce fresh updater artifacts. Earlier stale `.sig` and `.nsis.zip` files made the release state ambiguous.

## Evidence

- The first strict release gate removed stale updater files and rebuilt `G-Music_0.1.0_x64-setup.exe`.
- Tauri then logged `Decrypting updater signing key, expect a prompt for password` and failed with `incorrect updater private key password: No process is on the other end of the pipe`.
- Local `@tauri-apps/cli` is `2.11.3`; its changelog states that some empty-password updater keys generated by earlier 2.9.3-2.10.0 versions must be regenerated.
- Direct `tauri signer sign --private-key-path ..\keys\g-music.key --password=` worked after regenerating the key, proving the new key and empty-password signing path were valid.
- `tauri build --ci` avoided the interactive password prompt. The release script then signed the fresh setup executable with an explicit `tauri signer sign --password=` step.

## Root Cause

The release build path combined a stale/broken empty-password signing key with an interactive signing prompt path. Without `--ci`, Tauri attempted to prompt for a password in a non-interactive process. The script also expected an outdated `.nsis.zip` updater artifact, while Tauri 2.11 NSIS output for this build uses the setup executable plus `.exe.sig`.

## Why The Issue Escaped Detection

Sprint 3 validated the local setup executable only. Stale updater artifacts from 2026-06-27 were still present, so filesystem inspection could make updater signing look more complete than it was.

## Proposed Prevention

- Remove stale updater artifacts before release validation.
- Run Tauri release builds with `--ci`.
- Require fresh timestamps after build start for every expected updater artifact.
- Keep the Tauri public key in `tauri.conf.json` synchronized with the gitignored local private key.
- Treat Tauri version-specific artifact names as part of the validation contract instead of assuming older `.nsis.zip` output.

## Resolution

On 2026-07-03, the local signing key was backed up and regenerated with `@tauri-apps/cli` 2.11.3. The updater endpoint was corrected to `Freshair129/G-Music`, and `scripts\build_installer.ps1 -WithUpdaterArtifacts` passed with fresh artifacts:

- `G-Music_0.1.0_x64-setup.exe`: `53,282,201` bytes, LastWriteTime `2026-07-03 17:16:22`.
- `G-Music_0.1.0_x64-setup.exe.sig`: `416` bytes, LastWriteTime `2026-07-03 17:16:25`.

The script now builds the NSIS setup first, then signs it explicitly. A non-zero Tauri wrapper exit is allowed only when the setup executable is fresh, the build log contains the NSIS success sentinel, and no build log contains `Error` or `failed`; the explicit signer step must still exit successfully.
